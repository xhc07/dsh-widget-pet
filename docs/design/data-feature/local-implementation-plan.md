# 本地数据功能实现规划（先本地，后官方）

> 状态：设计阶段，未改插件代码。  
> 正式版本 2.2.1 保持不变。

## 1. 目标

先完成不依赖官方 zip 的本地功能：

1. 图表支持总跨度和每柱跨度；
2. 数据设置页：本地 JSON 导出；
3. 数据清理；
4. 为后续官方导入预留数据源接口。

官方 zip 导入、官方格式导出暂缓。

## 2. 当前本地数据

文件：

```text
~/.dsh/.dshcp-usage.json
~/.dsh/.dshcp-usage-archive.json   # 有超期数据时才存在
```

当前保留：

| 数据 | 保留 |
|---|---|
| events 逐轮明细 | 90 天 / 2 万条 |
| history 逐日汇总 | 365 天 |
| archive.events | 20 万条 |
| archive.history | 不按天删除 |
| accounting.books[].days | 不按天删除 |

自动清理发生在写入时，不是定时器。

## 3. 图表跨度

### 选项

- 总跨度：7 / 30 / 90 / 180 / 365 天
- 每柱跨度：1天 / 1周 / 2周 / 1月 / 3月

### 约束

```text
每柱跨度 <= 总跨度
柱数 = ceil(总跨度 / 每柱跨度)
```

非法组合在 UI 中禁用或自动夹取。365 天 + 1 天/柱允许但提示“柱子可能过密”。

### 数据来源（本地版）

```
某日总额 = ledger.history[day]（优先）
        若 history 没有，则 events 当天 cost 合计
        两者都没有 = 0
```

模型/对话明细仍来自 events；90 天前没有逐轮明细，只能显示日总额。

### 性能

当前 `usageRecords()` 会计算未使用的 `all.days`，且每一天重新扫 events，成本是 O(天数 × 事件数)。

计划：

- 图表只读取一次逐日汇总；
- 按桶累加，O(总天数)；
- 模型/对话详情才扫描 events；
- 面板打开时计算一次，导入/刷新时失效缓存。

## 4. 数据设置页

在设置中新增「数据」大类，首版本地版包含：

### 概览

- 主账本大小、事件数、逐日汇总天数
- 归档是否存在、大小、事件数
- 最早/最新数据日期
- 当前保留策略

### 导出

- 勾选「插件 JSON」：导出主账本 + 归档 + 元信息。
- 可选日期范围。
- 生成下载文件，不修改原数据。

建议 schema：

```json
{
  "schema": "dsh-widget-pet-usage",
  "version": 1,
  "exportedAt": "2026-11-25T...+08:00",
  "range": { "start": "2026-10-01", "end": "2026-11-25" },
  "ledger": {},
  "archive": {}
}
```

### 清理

建议操作：

1. 清理归档（删除 archive.events / archive.history，可保留空文件）
2. 清理旧逐轮明细（只留最近 N 天 events）
3. 清空全部本地用量（强确认 + 自动备份）

清理前写备份文件；不删除 `.dshcp-turn.json`，它只是轮次序号。

## 5. 本地 JSON 导入

首版可以先不做；如果做，需：

- schema/version 校验；
- 合并还是替换；
- 重复键处理；
- 导入前备份；
- 导入后重建汇总缓存。

## 6. 后续官方导入的接口预留

本地图表数据源抽象为：

```js
getDailySeries(range) -> [{ date, total, models, source }]
```

后续官方导入只是给这个接口增加一个 source：

```text
official 有实际行 -> source='official'
否则             -> source='local'
```

不需要改图表主体。

## 7. 官方优先/本地回退（后续）

已确认规则：

- 按实际存在官方 cost 行的日期判断；
- 同一天只取一个来源，绝不相加；
- 导入前弹窗显示：
  - 官方覆盖日期
  - 本地回退日期
  - 同一天官方/本地金额差异
  - 重复/冲突行数
- 官方数据独立存放，不写进本地 history/events。

风险：

- 官方是账号账单，包含第三方/其他 key/工具服务；
- 本地 history 是同一账号的余额观测；
- 本地 events 才是 DSH 自己的逐轮记录；
- 官方日期没有对话 ID，按对话只能回退本地并标记。

## 8. 两套账本与第三方中转

### 8.1 逐轮直接消费（events）

来源：`assistant/message` 的真实 `usage`。

- 记录：model、cost、tokens、sessionId、sessionName。
- 用于：最近一轮、上轮消费、详细用量的模型/对话、本地事件统计。
- 价格：本地内置 DeepSeek 价目表。
- 未知模型会落到 `_default`（DeepSeek Flash 基准价），所以第三方中转模型的金额只是估算，不是中转站真实扣费。

### 8.2 余额观测（history/accounting）

来源：DeepSeek 官方余额接口。

- 记录：每天余额下降 → 余额观测/校正 → history。
- 用于：余额、今日已用、徽章、近 7 天/图表日总额（`daySummary` 优先余额观测）。
- 不包含：第三方中转站自己的独立计费；除非它也扣同一个官方账号余额。

### 8.3 实际表现

| 场景 | events / 详细用量 | 余额与图表总额 |
|---|---|---|
| 官方 API 调用 | 记录 | 余额下降，记录 |
| 第三方中转（独立计费） | 记录，按本地 DeepSeek 价目表估算 | 官方余额不变；通常不进图表总额 |
| 第三方中转使用同一个官方 key | 记录 | 官方余额下降，图表总额可能包含，但无法按调用方拆分 |
| 没有余额观测/读不到余额 | 记录 | `daySummary` 回退 eventEstimate，此时本地 events（含第三方）可能进入图表 |
| 同日有余额观测 | 记录 | 以余额观测为准，不用 events 覆盖 |

### 8.4 图表含义

- 有余额观测时，图表柱子是“账号余额下降”，不是“本地逐轮消费合计”。
- 详细用量的模型行是“本地逐轮估算”，所以模型行相加可能不等于图表总额。
- 第三方中转用量会被记录在 events/详细用量里，但在有余额观测的日期不会计入图表总额。
- 如果希望第三方用量“看得见”，需要额外提供“本地逐轮估算”图表/开关，而不是把它混进官方余额柱。
- 导入官方 zip 后，官方日优先会进一步把图表限定为官方账号账单；第三方独立中转仍只在本地 events。

### 8.5 建议的数据源展示

后续图表至少区分：

- `官方账单/余额观测`
- `本地逐轮估算`
- `混合（按日回退）`

否则用户会误以为“图表总额 = 详细用量模型合计”。

## 9. 余额观测、充值与延迟扣费

### 9.1 当前逻辑

`observeBalance` 每次采样只比较本次余额和上次余额：

```text
本次 < 上次 → 记为 debit（消费）
本次 > 上次 → 记为 credit（充值/余额增加）
本次 = 上次 → 不变
```

`observedAmount` 只取 debit，不把 credit 当消费；余额增加不会让“今日已用”变负。

余额每 60 秒刷新一次（`BALANCE_TTL_MS`）。每天是一行 accounting 记录，记录 opening/last 余额、debit、credit。

### 9.2 充值发生在延迟扣费期间会怎样

分情况：

| 采样顺序 | 结果 |
|---|---|
| 先采到消费下降，再采到充值上升 | debit 和 credit 分别记录，消费正确；会因 credit 出现“待核对余额调整” |
| 先采到充值上升，再采到延迟消费下降 | 充值记 credit，消费记 debit；消费仍正确 |
| 充值和延迟消费发生在同一次 60 秒采样之间，净余额上升 | 只看到 credit，消费被充值掩盖，可能漏记 |
| 充值和延迟消费同一次采样之间，净余额下降 | 只看到净 debit，消费被低估 |
| 充值后余额上升，延迟消费尚未扣款，当天结束 | 当天可能记了 credit，消费记到次日或更晚 |
| 充值金额刚好抵消延迟消费 | 净余额不变，消费完全不可见，甚至不会触发 credit 标记 |

所以：

- **不会把充值误算成消费**；
- 但**可能漏记/低估延迟消费**，尤其是充值和扣费落在同一个采样窗口；
- 跨日时还会出现消费归属日偏移；
- 余额增加会触发 `needsReview`（待核对余额调整），但净额不变时可能连标记都没有；
- 校正窗口可以人工填 `credits` / `otherDebits`，但已经净掉的消费无法从余额变化中反推。

### 9.3 对第三方中转的影响

第三方中转如果是独立计费，不扣官方余额，不会造成这种充值抵消；它只存在于本地 events。

如果第三方或其他客户端使用同一个官方账号/API key，它们和官方消费一样会体现在余额下降中，无法按调用方拆分。

### 9.4 缓解

1. 提高余额采样频率只能缩小窗口，不能消除延迟扣费。
2. 充值前后保留手动校正记录。
3. 用本地 events 与余额观测交叉核对，标出差异。
4. 用官方导出账单做最终对账；官方导出是账单口径，不受采样窗口影响。
5. 后续数据功能可显示“余额观测 vs 本地事件估算”的差异，而不是强行合并。

## 10. 余额采样间隔

当前是双 60 秒：

- 前端 `BALANCE_MS = 60000`
- 宿主 `BALANCE_TTL_MS = 60000`

另有：

- 任务完成后的 4 秒 / 15 秒强制刷新
- 手动刷新
- 页面重新可见时，超过 60 秒会刷新

### 能否让用户选

可以，但需要同时处理两层：

1. 前端 interval 改成设置值；
2. 当设置值小于 60 秒时，请求必须带 `?refresh=1` 绕过宿主缓存，或者降低宿主 TTL。

如果只改前端 interval，不绕过宿主缓存，30 秒请求仍会拿到 60 秒内的旧数据，没有意义。

### 用户提出的设置结构

采样设置右侧放「默认」按钮：

- 默认开启且高亮；
- 默认模式使用原有 60 秒请求规则和宿主缓存；
- 不使用自定义规则，避免口径不一致；
- 关闭默认时进入自定义模式；
- 关闭默认时弹出高危确认。

自定义模式：

- 滑块范围 1–300 秒；
- 滑块气泡显示当前秒数；
- 右侧显示秒数；
- 点击秒数可输入 1–999；
- 输入值需要夹取/校验，避免溢出和非法值。

实现注意：

- 1–59 秒：每次请求必须带 `?refresh=1` 绕过宿主 60 秒缓存；
- 60 秒：等同默认；
- 61–999 秒：可以使用普通请求，但界面滑块最大 300，输入可超出滑块范围；
- 1 秒会产生每分钟 60 次余额请求，必须高危提示。

### 注释

自定义模式下方同时说明两类风险：

- 过低：请求更频繁，可能限流、增加耗电；1 秒风险最高。
- 过高：刷新更慢，充值和延迟扣费更容易落在同一窗口，漏记风险增加。

低于 60 秒时，滑块下方额外显示红色风险注释；高于 60 秒使用普通颜色注释。

### 什么时候弹高危

不做轮询，也不按每一格弹：

- 拖动过程中只更新滑块、气泡、秒数和注释；
- 释放滑块或输入提交时，比较旧值和新值；
- 只有**跨过 60 秒阈值**时弹一次高危确认；
- 低于 60 秒内部继续调整，不重复弹；
- 高于 60 秒内部继续调整，不重复弹；
- 取消则恢复旧值。

这样不需要定时检测，成本和普通滑块 input/change 一样。

默认值仍是 60 秒；默认模式是安全路径，自定义模式是用户自负风险。

### 限制

采样更频繁只能缩小“充值和延迟扣费落在同一窗口”的概率，不能彻底解决：

- 两者仍可能在同一个间隔内净额抵消；
- 余额接口可能延迟；
- 跨日归属仍可能发生。

最终仍应使用官方导出账单对账。
