> 样本目录：`DSH-DesktopPet/testdata/platform-exports/`

## 1. 样本文件

| 文件 | 原始大小 | 覆盖 | 官方总计 |
|---|---:|---|---:|
| `usage_data_2026-10-01_2026-10-31.zip` | 5,800 B | 实际有数据：10-24 ~ 10-29，6 天 | ¥5.847955 |
| `usage_data_2026-10-27_2026-11-25.zip` | 29,943 B | 实际有数据：10-27 ~ 11-25，26 天 | ¥96.895392 |
| `usage_data_2026-11-01_2026-11-25.zip` | 27,277 B | 实际有数据：11-01 ~ 11-25，23 天 | ¥94.375895 |

三个 zip 内各有两个 CSV：

- `cost-*.csv`
- `amount-*.csv`

两个 CSV 都是：

- UTF-8 **带 BOM**
- CRLF
- 日期边界为 `+08:00`，即北京时间
- 金额币种 CNY
- 日期区间不补零：没有用量的日期不会出现

## 2. CSV 字段

### cost

```text
user_id,start_time_iso,end_time_iso,model,name,wallet_type,cost,currency
```

- 按天 × 模型 × 钱包类型汇总金额。
- `wallet_type`：`Granted` / `Paid`。
- 30 天样本：Granted ¥1.748923，Paid ¥95.146469。
- `model` 为空时，`name` 是服务项，例如：
  - `server-tool-search`
  - `tool-search`

### amount

```text
user_id,start_time_iso,end_time_iso,model,name,api_key_name,api_key,type,price,amount
```

- 按天 × 模型 × 计费项给出数量和单价。
- `type` 包括：
  - `input_cache_hit_tokens`
  - `input_cache_miss_tokens`
  - `output_tokens`
  - `request_count`
  - `function_call`
- `amount` 是 token 数/请求数/调用次数，不是金额。
- 金额应等于 `amount × price`。
- 已逐日核对：`cost` 总额与 `amount × price` 总额一致（30 天均为 ¥96.895392）。

## 3. 峰谷信息

30 天样本中，同一个计费项存在两档单价，正好是 2 倍关系：

| 类型 | 低价 | 高价 |
|---|---:|---:|
| input_cache_hit | 0.00000002 | 0.00000004 |
| input_cache_miss | 0.000001 | 0.000002 |
| output | 0.000004 | 0.000008 |

高价位对应高峰时段。30 天中：

- 低价段模型费用：¥83.2182
- 高价段模型费用：¥13.2772
- 工具/服务费用：¥0.40
- request_count：6101 次
- function_call：31 次零价 + 80 次 ¥0.005

因此：

- `cost` 只给每天/模型/钱包总额，**不直接拆峰谷**。
- `amount` 的 `price` 可以还原峰谷 token 和峰谷费用。
- 工具/搜索服务是独立服务项，不应显示成某个模型。

## 4. 重叠与去重

三个导出有大量重叠日期：

- cost：37 个唯一键，34 个键在多个文件中出现
- amount：146 个唯一键，134 个键在多个文件中出现
- 相同键的金额/数量**全部一致，没有冲突**

去重键建议：

- cost：`user_id + start + end + model + name + wallet_type + currency`
- amount：`user_id + start + end + model + name + api_key_name + api_key + type + price`

不能简单按日期追加，否则重叠区间会翻倍。

## 5. 与本地账本对比

本地 `.dshcp-usage.json` 当前 25 天、244 条事件、约 44.9 KB。

30 天对比：

- 官方总费用：¥96.895392
- 本地逐日 history 合计：¥79.730475
- 本地逐轮 events 合计：¥65.266729

差异原因：

- 官方包含 Granted/Paid 全部钱包；本地余额观测不一定反映赠金。
- 官方包含工具/搜索等非模型服务。
- 官方 request_count 6101 次，远高于本地 244 条逐轮事件；本地只记录 DSH 插件观察到的轮次，平台包含其他调用。
- 官方是账单口径，本地是余额观测 + 本地事件估算，不能互相覆盖。

结论：**官方数据应作为独立数据集导入**，不能直接写进本地 `history`，也不能覆盖本地对话明细。

## 6. 对话明细的限制

官方导出没有：

- session ID
- 对话标题
- 每轮记录

所以官方数据只能支持：

- 按天
- 按模型
- 按钱包类型
- 按计费项/峰谷
- 工具/服务费用

不能支持官方数据的“按对话”拆分。按对话仍只能来自本地账本。

## 7. 图表跨度可行性

可行，但需要聚合：

- 7 天：按日，7 根
- 30 天：按日，30 根
- 180 天：按周，约 26 根
- 365 天：按周或月，约 52 或 12 根

性能注意：

- 当前 `all.days` 对每个日期都重新扫一遍事件，是 O(天数 × 事件数)。
- 30 天样本很小，但 365 天不该这样算。
- 应改为一次扫描/读取逐日汇总，再按桶聚合。
- 官方数据行数很少（30 天 cost+amount 约 183 行），导入和聚合开销可忽略。

## 8. 建议的存储与展示架构

### 导入数据独立存放

建议新增独立文件，例如：

```text
.dshcp-platform-usage.json
```

不要混入 `.dshcp-usage.json` 的 events/history。

结构可存：

- 原始 cost 行
- 原始 amount 行
- 导入文件元信息
- 按日聚合缓存

### 图表优先级

建议：

1. 有官方导入数据：优先显示官方每日费用；
2. 没有官方数据：回退到本地 history；
3. 图表旁标注“官方导入 / 本地估算”，避免混用。

### 详细用量

- 本地数据：模型 + 对话 + 本地 token；
- 官方数据：模型 + 钱包 + 峰谷 token/费用 + 工具服务；
- 官方数据没有对话维度，不伪造。

### 数据设置页

可新增“数据”大类：

- 导入官方 zip / csv
- 导出本地 JSON
- 导出官方数据 JSON（可选）
- 清理本地明细/归档/官方导入
- 导入前备份、导入摘要、冲突提示

## 11. 推荐实现方案（仅规划，未写代码）

### 11.1 官方数据独立存储

新增独立数据文件，例如：

```text
.dshcp-platform-usage.json
```

不写入 `.dshcp-usage.json` 的 `events` / `history`。

存两类原始行：

- cost 行
- amount 行

再加导入元信息：

- 文件名
- 文件声明的日期范围
- 实际有数据的日期集合
- 导入时间
- 行数、重复数、冲突数

### 11.2 “官方有的用官方，没有的回退本地”

可行，按**实际有官方行的日期**判断：

```text
某天：
  官方有该天 cost 行 → 用官方日总额
  官方没有该天行，但本地有 history/events → 用本地
  两边都没有 → 0
```

不建议用“文件声明范围”判断，因为官方文件可能声明 10-01～10-31，但只有 10-24～10-29 有数据；不能把没有行的日子强行当成官方 0。

注意事项：

- 官方包含 Granted/Paid、工具/搜索服务；本地 history 是余额观测。
- 同一天不要官方 + 本地相加，否则重复计费。
- 图表要显示来源：官方 / 本地 / 混合。
- 按日看是干净的；按模型看，官方日只有官方模型/钱包/计费项，本地日只有本地模型。
- **官方没有对话 ID**：官方日期的“按对话”无法从官方数据还原，只能显示“官方导出无对话明细”，或另外展示本地对话（标记为本地）。

### 11.3 图表两个跨度

可做成两个独立选择：

- **总显示跨度**：7 / 30 / 180 / 365 天
- **每柱跨度**：1 天 / 1 周 / 1 月（或按需要增加 2 周、3 月）

计算：

```text
柱数 = ceil(总跨度 / 每柱跨度)
```

示例：

- 总 30 天 / 每柱 1 天 = 30 根
- 总 180 天 / 每柱 7 天 = 26 根
- 总 365 天 / 每柱 7 天 = 53 根
- 总 365 天 / 每柱 30 天 = 13 根

每根柱子内按天汇总，来源可能是官方+本地混合；悬浮气泡显示：

- 总费用
- 官方天数 / 本地天数
- 日期范围

性能：

- 只读取逐日汇总，一次 O(天数) 聚合，不扫 2 万条事件。
- 365 天/每柱 1 天时仍会有 365 根 DOM，需限制最小柱宽或提示；建议 365 天默认每柱 1 周。
- 官方数据行数很小，不会增加轮询开销。

### 11.4 导入冲突预览

导入流程建议：

1. 解析 zip/CSV，不立即写盘；
2. 按唯一键与已导入数据比较；
3. 显示摘要：
   - 新增行
   - 完全重复
   - 金额/数量冲突
4. 冲突列表显示：日期、模型/服务、钱包/类型、旧值、新值、差值；
5. 用户选择：
   - 全部使用新值
   - 全部保留旧值
   - 逐项选择
6. 确认后才写盘，并先备份旧官方数据。

本次三个样本：34 个 cost 重复键、134 个 amount 重复键，全部一致，没有冲突。

### 11.5 导出

- 本地数据导出 JSON（主账本/归档/设置可按需）。
- 官方导入数据导出 JSON。
- 可选导出官方兼容 CSV（cost/amount），但 platform.deepseek.com 是否支持反向导入尚未验证，不能承诺。

### 11.6 清理

- 清理官方导入数据（按文件或全部）。
- 清理本地归档。
- 清理本地旧明细，保留逐日汇总。
- 清空全部用量（强确认 + 备份）。

### 11.7 性能结论

- 导入/导出/清理都是一次性操作。
- 日常轮询不读官方数据，几乎没有额外开销。
- 图表需要避免当前 `all.days` 的 O(天数×事件数) 计算；改成逐日汇总一次性建桶。
- 官方 30 天样本只有约 183 行，365 天也不过数千行。

## 13. 已确认方向与风险结论（2026-11-25）

### 13.1 官方优先、本地回退

- 按实际存在官方 cost 行的日期判断官方优先。
- 例如“上月”只有 10-24～10-29 用过官方 API，就只把这些日期认作官方有数据；其余日期回退本地。
- 同一天绝不把官方和本地相加。
- 导入时弹窗/预览告知：
  - 官方覆盖日期
  - 本地回退日期
  - 同一天官方与本地金额差异
  - 完全重复、冲突行数

### 13.2 是否会造成“第三方 + 官方”双记

不会因为“相加”而双记，但有一个口径问题需要保留提示：

- 官方导出是官方账号的账单，包含该账号下所有 API key 的调用，可能包含第三方客户端和工具服务。
- 本地 history 是该账号余额下降的观测，本质上也是同一账号的用量，不是另一套独立账本。
- 本地 events 才是 DSH 自己逐轮记录的部分。
- 若按“官方日优先、本地日回退”逐日取一个来源，不会把同一天的量算两遍。
- 但官方日可能显示第三方/其他 key 的用量，本地日可能只有本地观测；图表必须标记来源。
- **不能采用官方日 + 本地日同天相加**，也不能把官方数据直接写进本地 history。
- 如果用户目标只是“DSH 自己的用量”，官方导出无法区分第三方，只能作为“账号账单口径”单独展示。

### 13.3 官方日期没有对话明细

- 用户选择：官方没有对话数据时，以本地为准。
- 实现时必须标记“本地对话明细”，并接受：
  - 官方日总额可能不等于本地对话行合计；
  - 官方日按对话视图不能假装完整。
- 可选展示方式：
  - 官方日总额下方标注“对话明细来自本地，可能不完整”；
  - 或按对话视图只展示本地有明细的日期。

### 13.4 图表跨度

已确认选项：

- 总跨度：7 / 30 / 90 / 180 / 365 天
- 每柱跨度：1 天 / 1 周 / 2 周 / 1 月 / 3 月
- 每柱跨度不得大于总跨度；UI 需自动禁用/夹取非法组合。
- 365 天默认每柱 1 周；允许 1 天但需提示柱子过密。

### 13.5 导出界面想法

用户希望导出时勾选：

- 官方格式
- 插件 JSON 格式
- 可同时勾选

官方格式：

- zip 包
- 内部文件名与官方一致：
  - `cost-<start>_<end>.csv`
  - `amount-<start>_<end>.csv`
- 可选按钮/勾选“添加 _pet 后缀”，让 zip 变成：
  - `usage_data_<start>_<end>_pet.zip`
- 用于和官方原始导出区分。

可行性结论：

- **可以**对“从官方 zip 导入并保留下来的原始行”重新生成同结构 zip/CSV。
- **不能**把纯本地数据无损伪造成官方格式：
  - 本地没有官方 `user_id`、`wallet_type`、`api_key_name`、`cache_hit/miss` 拆分、`request_count`、`function_call` 等字段。
  - 只能生成近似数据，不能称为“完全和官方一样”。
- 因此官方格式导出应只导出**官方来源的行**；本地数据走 JSON。若选择官方格式但当前没有官方导入数据，应禁用或明确警告。
- platform.deepseek.com 是否接受反向导入这个 zip 尚未验证；只能保证格式/命名一致，不能保证平台接受。
